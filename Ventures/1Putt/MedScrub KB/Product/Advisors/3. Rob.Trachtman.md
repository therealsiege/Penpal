### Product Overview
- MedScrubbing is a desktop application that provides PHI de-identification and AI workspace capabilities for healthcare providers
- Core functionality: de-identifies patient data before sending to consumer LLMs (like GPT-4), stores variables in Redis session, then re-identifies data when it returns - seamless to the physician
- Multiple access modalities supported: desktop app, HTTP API, MCP server, and mobile app
- Positioned as an affordable alternative to expensive solutions like Bridge, Doximity, and Navina for smaller practices
### Technical Capabilities and Integrations
- **EHR Connectivity**: Bidirectional integration with Epic, Athena, Oracle, and various mid-level EHR systems
- **HIE Integration**: Enriches data from Health Information Exchange providers using newer HIE API middleware abstractions
- **Clinical Data Repository**: Stores patient data with sync capabilities (manual or scheduled cadence)
- **CDS Hooks**: Available for some EHRs to display AI-generated insights directly in the EHR during patient view events
- **Vim Canvas Integration**: For EHRs that don't support backend bulk FHIR communication (like ECW), uses Vim app that launches within patient context using Vim browser tool
### Key Features and Use Cases
- **Safe Chat**: Select patients from EHR data and chat about them with de-identified data protection
- **Pre-visit Planning**: Generates comprehensive summaries for upcoming appointments, handling complex patient conditions lists and preparing providers for visits
- **Automation Tools**: Building library of healthcare workflow automations (similar to Codex's approach) that combine prompting with integration capabilities
- **Document References**: AI-generated summaries can be inserted as document references in EHR
- **Mobile App**: Focused on between-care notifications and interactions (different feature set than desktop)
### Market Positioning Discussion
- **Primary Target**: Small to mid-sized practices and solo practitioners who lack budget and technical capabilities for enterprise-scale AI solutions
- **Market Analogy**: Described as "Codex or Cloud for medical practice" - a surface work area between the business and LLMs, similar to how Codex serves developers
- **Challenge Identified**: People aren't currently working this way - different roles (MA, doctor, billing) use different tools in separate workflows, making organizational adoption difficult
- **Value Proposition**: Even with BAAs in place, HIPAA's minimum necessary requirements mean preventing patient data from going to LLM providers is important - MedScrubbing addresses this
### Rob's Strategic Recommendations
- **Solo Practitioners Preferred**: Small practices (solo or 1-2 employees) are better target than hospital departments because they're more entrepreneurial, willing to be early adopters, and need to do many things without hiring more staff
- **Department-Specific Approach Less Favorable**: Niching down to specific hospital functions (like utilization review) is harder due to incumbent solutions, need for deep subject matter expertise, and difficulty building trust as a small entity
- **Networking Opportunity**: Suggested connecting with Polus Mui from Health Tech Nerds community - runs solo practice, has engineer friend, building similar technology, has community of technical doctors who would be interested in testing
### Prior Authorization Landscape
- **Current Regulatory Environment**: HCI2 mandate pushing EHRs to implement CDS hooks, but they're at varying capability levels
- **Epic's Role**: Only serves its own customer base, not relevant for smaller practices
- **DaVinci Standards**: New FHIR-based standards are better than X12, but implementation challenges remain - payers will support them because required, but doesn't solve the underlying complexity
- **Market Reality**: Multiple AI tools emerging (phone automation, web navigation, RPA), but all tend to be fragile when expanding beyond simple initial pilots
- **Prior Auth Complexity**: Gets very complicated with recurring appointments, complex protocols, third-party reviews - intentionally designed as a hoop to jump through
- **Best LLM Use Case**: Matching published payer policies (unstructured PDFs) against clinical records to identify documentation gaps - clean use case that doesn't claim to solve entire prior auth workflow
- **Realistic Expectation**: Human-in-the-middle approach may be best achievable outcome currently, similar to HL7v2's persistent complexity
