# FHIR Constraints

> Healthie does NOT use FHIR. This is a complete paradigm shift — proprietary GraphQL to FHIR R4 REST. Requires full data model transformation.

**See also:** [Capability Mapping](Capability%20Mapping.md) | [Phases](Phases.md) | [Risks](Risks.md) | [FHIR Glossary](FHIR%20R4%20Glossary.md)

## Migration Strategy

1. **Export** — Extract data from Healthie via GraphQL API (bulk queries)
2. **Transform** — ETL pipeline: Healthie data models → FHIR R4 resources
3. **Validate** — Validate FHIR resources against Medplum schemas
4. **Import** — Load into Medplum via FHIR Batch/Transaction bundles
5. **Verify** — Data integrity and completeness checks

## ID Constraints

Medplum enforces FHIR R4 ID rules:

| Constraint | FHIR R4 Rule |
|-----------|-------------|
| Resource IDs | `[A-Za-z0-9\-\.]{1,64}` — max 64 characters |
| Healthie IDs | Database serial IDs or UUIDs — no FHIR constraints |
| **Migration requirement** | Map Healthie IDs to FHIR-compliant IDs, OR use Medplum-generated IDs with a cross-reference table |

## FHIR Constraints to Watch

| Constraint | Details |
|-----------|---------|
| Resource IDs | 64 char max, alphanumeric + hyphens/periods only |
| String fields | Max 1,048,576 chars (1MB) per FHIR spec |
| DateTime format | ISO 8601: `YYYY-MM-DDThh:mm:ss+zz:zz` — Healthie may differ |
| Coding bindings | Required value sets (e.g., AdministrativeGender: male\|female\|other\|unknown) |
| Versioning | Medplum tracks `meta.versionId` — every update creates new version (Healthie has no concept of this) |
| Bundles | Transaction bundles for atomic multi-resource operations — use for migration imports to maintain referential integrity |

## Resource Validation

- Medplum validates all resources against FHIR R4 StructureDefinitions on write
- Required fields vary per resource (e.g., Patient requires no fields, Observation requires status + code)
- Cardinality enforced: `1..1` and `1..*` fields must be present
- Healthie validation rules do NOT map 1:1 to FHIR constraints

## Data Model Transformation Details

For the full paradigm shift comparison (query language, data shape, relationships, coding systems), see [Capability Mapping — API Paradigm Shift](Capability%20Mapping.md#api-paradigm-shift).

Key transformation rules:

| Healthie Pattern | FHIR Transformation |
|-----------------|---------------------|
| Flat/nested objects | FHIR resources with `Reference(ResourceType/id)` |
| Foreign keys (`patient_id: "123"`) | `{ "reference": "Patient/abc-123" }` |
| Custom fields | FHIR Extensions (define StructureDefinition) |
| Free-text / internal codes | CodeableConcept bound to SNOMED CT, LOINC, ICD-10, RxNorm, CPT |
| No versioning | `meta.versionId` auto-incremented on every update |
| Custom audit trails | AuditEvent resources (auto-generated by Medplum) |
