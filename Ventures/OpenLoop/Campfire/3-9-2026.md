### HeyRevia Cancellation Automation Performance

- Current success rate feels low with only 200 tickets per day being handled automatically
- Based on February data showing ~20,000 total monthly tickets, HeyRevia is only handling about 50% of potential work - complicated cases are being missed
- Main gaps identified: Med-B cancellations slipping through, unknown categories representing work HeyRevia isn't handling
- Need to expand to refund automation, but this requires unique generated links rather than static links to prevent security issues
- Session portal link expected to go live today, which should help increase automation coverage
- Top three products aren't included in retention rule, causing tickets to be canceled without applying coupon or capturing reasons
- Some savable cases (medical impact concerns, allergies) are going to humans who just cancel instead of being properly routed

### Customer Support Channel Strategy

- Team lacks clarity on preferred customer contact method - need to decide between chat, email, or phone
- Current volume distribution shows email and phone as top channels, but data may not be accurate due to chat ticket linkages
- Chris indicated chat has become highest volume contact point, contradicting shown data - need accurate numbers to make prioritization decisions
- Strategy discussion around chat-first approach, with recommendation to focus on chat and email as more easily automatable than phone
- Brick and mortar implementation already using email and chat only (no phone line)
- Rescheduling remains a high-volume issue with approximately 13,000 phone contacts last month

### Chat Automation Development

- Major coordination gap identified: Leo and NJ have been working on Amazon Connect chat automation in isolation without connecting with broader automation team
- Current chat automation only handles generic responses (e.g., where to find intake forms), not intelligent automation
- Need to implement same cancellation and rescheduling flows available in email automation for chat
- Amazon Connect chats create tickets that go to queue for human pickup within 5 minutes
- Proposal to use ticket-based function calls for cancellation requests during human chat interactions
- Chat automation readiness exists but waiting for organizational prioritization
- Approximately 700 cancellation requests per day via chat over the weekend

### Two-in-One Product Rollout Success

- Launch showing strong initial results: 142 patients prescribed double instead of quad
- 92 patients (65%) opened communications about clinical reasoning for change
- Only 4.3% of patients requested cancellation instead of accepting the change
- 192 patients saved from DQ who otherwise would have been disqualified
- Some providers not yet adhering to new option - likely due to recent training (went out Thursday) with typical one-week gap for provider education adoption
- Next steps include monitoring overall DQ rate impact and rolling out to Taurus
- Need to develop additional four-in-one options to eliminate backend email requirement

### Sync Conversion Efficiency Issues

- Hundreds of patients per day being unnecessarily converted to sync when not needed
- Two main causes identified: over-conservative providers and dose spot discrepancies that don't materially impact treatment
- Providers converting to sync for thyroid medications even when already addressed, and for minor dose spot conflicts
- Current process makes conversion too easy with perverse incentives - same pay rate regardless of sync vs async, no repercussions
- Proposal to add required checkbox and text explanation when converting to sync to create accountability
- Rebecca conducting individualized provider outreach for those significantly beyond mean conversion rates
- This impacts clinical efficiency OKR and cost of care as percent of revenue
- Opportunity to catch more issues upstream before reaching clinicians through better intake screening and AI expected outcomes work
- Summary review feature may help by showing clinical decision support about why not to convert to sync

### Team Coordination and Communication Gaps

- Significant disconnect between teams working on different parts of automation (HeyRevia, chat, clinical workflows)
- Leo and NJ working on Amazon Connect automation haven't been integrated with main automation team discussions
- Initial chat work was "skunkworks" effort when organizational priority wasn't given, not meant to be final solution
- Need for better data visibility across all support channels to make informed prioritization decisions
- Analytics dashboard exists in Toolbelt under patient support section for tracking key metrics

### Meeting Context

The team met to resolve domain ownership and API architecture questions for the payment checker story. The main challenge is that Scott has already built several APIs (ESL-51, ESL-53, ESL-54, ESL-1551) that span multiple domains, but the code currently lives in the payments domain.    The team needs to decide how to properly organize these APIs across domains (customer, product, EHR facade, payments/revenue) and determine the right architectural pattern for different consumers. 

### Core Problem

The payment checker API needs to retrieve Stripe subscriptions and invoice payment history for patients.  However, this requires assembling information across multiple domains:

- Getting patient information by email (EHR facade)
- Getting Stripe customer ID using that email
- Retrieving subscriptions and invoices from Stripe

Different consumers have different capabilities:

- **Zoho** can only pass patient ID and healthy org ID, and has API call limits, so needs a single aggregated endpoint
- **ClinicApp** can handle making multiple separate API calls before calling the final endpoint

### Key Architectural Decisions

**Stripe as a Black Box:** The team agreed that payments and revenue should be the only entry point to Stripe, acting as the system of record.   No other services should call Stripe directly. This keeps the system agnostic to the payment provider (could be Stripe, ChargeBee, or others in the future).    

**Domain Ownership Clarified:**

- Patient lookup by email: EHR facade (already exists)
- Stripe customer operations: Customer Reference Service (Diego's team is building this)
- Products by org: Product domain (Renato working on ESL-52)
- Subscriptions and invoices: Should live in payments and revenue domain as they're Stripe objects

**Aggregator vs À La Carte Pattern:** Scott is building both approaches - core APIs (à la carte) and aggregators that consume them (happy meal approach).  The aggregators handle different input formats from different consumers (Zoho, ClinicApp, etc.).  Curtis advocates for the system taking on the burden of understanding different inputs rather than making clients adapt. 

### Technical Approach Moving Forward

**Short-term Solution:** Scott will continue building in the payments domain but will structure the code in separate logical layers:  

- Core Stripe interaction layer (can be extracted later)
- Aggregator layer for Zoho (accepts patient ID, does lookups)
- Aggregator layer for ClinicApp (different requirements)
- Ensure code can run independently if moved to different domains

**Long-term Architecture:** The team acknowledged they have only about 30% of the information needed to make a perfect decision.  They agreed to:

- Deliver something workable now to learn more quickly
- Continue thinking about the topology and proper domain boundaries
- Expect patterns to emerge after building a few aggregators
- Make it easy to refactor when the right solution becomes clear

Curtis noted this likely needs additional architectural layers beyond what was originally anticipated, similar to early Stripe documentation but with more depth. 

### Outstanding Questions

**Where Should Aggregators Live?** The team discussed whether aggregators should:

- Live in the same repo as the core APIs
- Be separated into their own layer/service
- Be consumer-specific with different auth controls

There's concern about manageability as the number of aggregators grows to support different clients with different information needs.  

**Reference Data Service:** The team briefly discussed needing a service that can quickly retrieve reference data (like patient IDs, org IDs) without caring about the source system, potentially using caching. 

### Technical Blockers Resolved

Scott was blocked by hitting the 1,000 AWS role limit in his dev environment. Clint advised requesting increases to 1,500 (automatic) and 2,000 (may require approval) rather than deleting existing stacks.
