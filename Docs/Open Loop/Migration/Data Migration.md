# FHIR Constraints

> Healthie does NOT use FHIR. This is a complete paradigm shift — proprietary GraphQL to FHIR R4 REST. Requires full data model transformation.

**See also:** [Capability Mapping](Capability%20Mapping.md) | [Phases](Phases.md) | [Risks](Risks.md) | [FHIR Glossary](FHIR%20R4%20Glossary.md) | [Care Plans & Tasks](../Medplum/Care%20Plans%20&%20Tasks.md) | [Server Operations](../Medplum/Server%20Operations.md)

## Migration Strategy

1. **Export** — Extract data from Healthie via GraphQL API (bulk queries)
2. **Transform** — ETL pipeline: Healthie data models → FHIR R4 resources
3. **Validate** — Validate FHIR resources against Medplum schemas
4. **Import** — Load into Medplum via FHIR Batch/Transaction bundles
5. **Verify** — Data integrity and completeness checks

## ID Constraints

Medplum enforces FHIR R4 ID rules:

| Constraint | FHIR R4 Rule |
|-----------|-------------|
| Resource IDs | `[A-Za-z0-9\-\.]{1,64}` — max 64 characters |
| Healthie IDs | Database serial IDs or UUIDs — no FHIR constraints |
| **Migration requirement** | Map Healthie IDs to FHIR-compliant IDs, OR use Medplum-generated IDs with a cross-reference table |

## FHIR Constraints to Watch

| Constraint | Details |
|-----------|---------|
| Resource IDs | 64 char max, alphanumeric + hyphens/periods only |
| String fields | Max 1,048,576 chars (1MB) per FHIR spec |
| DateTime format | ISO 8601: `YYYY-MM-DDThh:mm:ss+zz:zz` — Healthie may differ |
| Coding bindings | Required value sets (e.g., AdministrativeGender: male\|female\|other\|unknown) |
| Versioning | Medplum tracks `meta.versionId` — every update creates new version (Healthie has no concept of this) |
| Bundles | Transaction bundles for atomic multi-resource operations — use for migration imports to maintain referential integrity |

## Resource Validation

- Medplum validates all resources against FHIR R4 StructureDefinitions on write
- Required fields vary per resource (e.g., Patient requires no fields, Observation requires status + code)
- Cardinality enforced: `1..1` and `1..*` fields must be present
- Healthie validation rules do NOT map 1:1 to FHIR constraints

## Data Model Transformation Details

For the full paradigm shift comparison (query language, data shape, relationships, coding systems), see [Capability Mapping — API Paradigm Shift](Capability%20Mapping.md#api-paradigm-shift).

Key transformation rules:

| Healthie Pattern | FHIR Transformation |
|-----------------|---------------------|
| Flat/nested objects | FHIR resources with `Reference(ResourceType/id)` |
| Foreign keys (`patient_id: "123"`) | `{ "reference": "Patient/abc-123" }` |
| Custom fields | FHIR Extensions (define StructureDefinition) |
| Free-text / internal codes | CodeableConcept bound to SNOMED CT, LOINC, ICD-10, RxNorm, CPT |
| No versioning | `meta.versionId` auto-incremented on every update |
| Custom audit trails | AuditEvent resources (auto-generated by Medplum) |

## Medplum Healthie Importer (Reference Implementation)

The Medplum codebase includes a **complete Healthie → FHIR importer** at `examples/medplum-healthie-importer/`. This is the definitive reference for OpenLoop's migration ETL.

**Path:** `examples/medplum-healthie-importer/src/`

### Module Map

| Module | Healthie Source | FHIR Target | Key Function |
|--------|----------------|-------------|--------------|
| `healthie/patient.ts` | `users` GraphQL query | `Patient` | `convertHealthiePatientToFhir()` — maps name, phone, gender, address, dietitian |
| `healthie/provider.ts` | `organizationMembers` | `Practitioner` + `PractitionerRole` | `convertHealthieProviderToPractitioner()` |
| `healthie/medication.ts` | medications | `MedicationRequest` | `convertHealthieMedicationToFhir()` |
| `healthie/allergy.ts` | `allergy_sensitivities` | `AllergyIntolerance` | `convertHealthieAllergyToFhir()` |
| `healthie/coverage.ts` | policies | `Coverage` | `convertHealthiePolicyToFhir()` |
| `healthie/document.ts` | documents | `DocumentReference` + `Binary` | `convertHealthieDocumentToFhir()` — downloads via expiring URLs |
| `healthie/questionnaire-response.ts` | `formAnswerGroups` | `QuestionnaireResponse` | `convertHealthieFormAnswerGroupToFhir()` |
| `healthie/clinical-activity.ts` | clinical activities | Clinical resources | Clinical note/activity conversion |
| `healthie/client.ts` | — | — | GraphQL client wrapper for Healthie API |

### Import Pipeline Pattern

The main bot (`import-healthie-patients.ts`) demonstrates the complete pipeline:

1. **Providers first** — batch upsert all `Practitioner` + `PractitionerRole` (follows Medplum's recommended sequencing)
2. **Paginate patient IDs** — cursor-based pagination from Healthie, supports `sinceLastUpdated` for incremental sync
3. **Per-patient bundles** — for each patient, fetch all clinical data in parallel (`Promise.all`), then submit as a single FHIR batch
4. **Conditional upserts** — every entry uses `PUT` with identifier query (`Patient?identifier=system|value`) for idempotency
5. **Continue on failure** — individual patient failures don't block the batch

### Key Patterns to Adopt

```typescript
// Conditional upsert — idempotent, safe to re-run
patientBundle.entry?.push({
  resource: fhirPatient,
  fullUrl: `urn:uuid:${generateId()}`,
  request: {
    method: 'PUT',
    url: `Patient?identifier=${HEALTHIE_USER_ID_SYSTEM}|${healthiePatient.id}`,
  },
});

// Conditional reference — link without knowing Medplum IDs
fhirPatient.generalPractitioner = [{
  identifier: { system: HEALTHIE_PROVIDER_ID_SYSTEM, value: healthiePatient.dietitian_id },
}];
```

## Migration Sequencing (from Medplum Docs)

Medplum recommends migrating data in FHIR dependency order. Source: `packages/docs/docs/migration/migration-sequence.md`

| Order | Data Element | FHIR Resources | Notes |
|-------|-------------|----------------|-------|
| 1 | Provider Demographics & Credentials | `Practitioner`, `PractitionerRole` | Link clinicians to clinical events |
| 2 | Shared Organizations | `Organization` | Multi-practice settings — each OpenLoop client |
| 3 | Patient Demographics | `Patient` | Foundational record referenced by everything |
| 4 | Problem List, Medication List | `Condition`, `MedicationRequest` | Current medical snapshot |
| 5 | Encounter History, Vitals, Labs | `Encounter`, `Observation`, `DiagnosticReport` | Longitudinal health data — backfill over time |

**Key principle:** Deliver immediate clinical value (patient snapshot) first, backfill longitudinal data over time.

## Adoption Strategy (from Medplum Docs)

Medplum recommends **phased adoption** (not big bang). Apply per data element type. Source: `packages/docs/docs/migration/adoption-stategy.md`

| Phase | Description | OpenLoop Mapping |
|-------|-------------|-----------------|
| 1. **Dual Write** | Write to both Healthie and Medplum on every update | Backend-only change, no user impact |
| 2. **Backfill** | Migrate historical data via ETL (Healthie importer bot) | Run incrementally with `sinceLastUpdated` filter |
| 3. **Read from Medplum** | UX reads from Medplum API (feature-flagged) | Clinic App switches data source per feature flag |
| 4. **Write to Medplum** | UX writes directly to Medplum, optional reverse sync to Healthie via Bot+Subscription | Partners API routes to Medplum adapter |
| 5. **Deprecate Healthie** | Remove old store, maintain read-only access for verification | Swap API key mapping in PartnerApi authorizer |

## Pipeline Strategies (Batches vs. Transactions)

From Medplum docs (`packages/docs/docs/migration/migration-pipelines.md`) and workshop Q&A:

| Strategy | Use Case | Limit | Behavior |
|----------|----------|-------|----------|
| **Batch** (`type: "batch"`) | Independent resources (patients, medications) | No hard limit (100+ can cause DB errors) | Each entry succeeds/fails independently |
| **Transaction** (`type: "transaction"`) | Related resources that must succeed together | 20 resources max | All-or-nothing, rolled back on failure |
| **Batch of transactions** | Best of both — group related resources in small transactions, batch them together | 20 per inner transaction | Atomic per group, independent across groups |

**Binary file migration:** Medplum auto-downloads external URLs in `DocumentReference.content[].attachment.url`. If Healthie provides pre-signed URLs, Medplum will fetch and store the file automatically.

## Code Mapping with ConceptMap $translate

For translating Healthie's internal codes to standard terminologies (SNOMED, LOINC, ICD-10, RxNorm):

**Server path:** `packages/server/src/fhir/operations/conceptmaptranslate.ts`
**Core logic:** `packages/core/src/fhirmapper/conceptmaptranslate.test.ts`

```
POST /ConceptMap/$translate
{
  "system": "http://healthie.com/codes/conditions",
  "code": "HT001",
  "targetSystem": "http://hl7.org/fhir/sid/icd-10-cm"
}
→ Returns: { "code": "I10", "display": "Essential hypertension" }
```

**OpenLoop strategy:**
1. Create `ConceptMap` resources mapping Healthie internal codes → standard terminologies
2. Use `$translate` in migration bots to auto-resolve codes during ETL
3. Use `$import` to bulk-load ConceptMap entries from existing mapping spreadsheets

## Automated Data Extraction ($extract)

For intake forms, `$extract` replaces custom bot code for standard data extraction:

**Server path:** `packages/server/src/fhir/operations/extract.ts`

```
POST /QuestionnaireResponse/{id}/$extract
→ Returns: Bundle of Observation, Condition, AllergyIntolerance resources
```

Questionnaire items annotated with LOINC/SNOMED codes and the `sdc-questionnaire-extraction` extension are automatically converted to discrete FHIR resources. See [Care Plans & Tasks — $extract](../Medplum/Care%20Plans%20&%20Tasks.md#questionnaire--structured-data-extraction) for full details.
