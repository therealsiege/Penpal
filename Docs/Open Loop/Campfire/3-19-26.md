### Access Policy Configuration & Best Practices

**Viewing Organization Membership**

- Organization membership is only visible in the JSON view, not in the UI edit view
- This is expected behavior as compartments are considered metadata on resources
- A ticket could be made to add this to the edit view

**Updating Compartments**

- The recommended method for adding patients to organizations is using the `setAccounts` operation
- When using `setAccounts`, compartments are automatically assigned
- Both singular `account` and plural `accounts` fields exist for backwards compatibility, but `accounts` plural is what's actually used
- Compartments field includes patient compartment and project compartment metadata

**Access Policy Requirements**

- Access policies require both a `resourceType` and a `criteria` field with compartment filter to properly restrict access
- Without the criteria field, the policy may still show all patients in the organization
- The criteria field performs the actual filtering at runtime when requests are sent to the server

**Parameterization vs Hard-Coding**

- Instead of hard-coding organization IDs, use parameterization with `$organization`
- This allows the same access policy to be applied across multiple tenants without creating duplicate policies

**Read-Only Fields**

- Access policies support a `readOnly` fields array to restrict which fields users can access

### JSON vs UI Resource Creation

- JSON is the source of truth and contains all functionality
- The UI may not include every bit of functionality available in the JSON
- Most customers send requests directly to the server and view changes in the UI rather than creating resources through the UI
- It's dealer's choice whether to use UI or JSON for resource creation, but JSON is recommended for validation

### Current API URL Structure and Technical Limitations

- Team discussed API path patterns for accessing resources across domains (e.g., getting products by org/config ID)
- Current limitation: Maximum three path levels deep for every endpoint
- Technical constraint: Each domain has its own API gateway, requiring a path prefix to determine which gateway to communicate with
- Enterprise API gateway acts as a proxy to domain-specific API gateways via VPC links
- Solution: Using query parameters for config ID instead of path parameters when crossing domains
- Example: `/products?config_id=X` instead of `/configs/{id}/products`
- Config ID only required for listing endpoints; specific resource requests (by ID) don't need it since the ID contains enough context

### Domain Architecture and Isolation Strategy

- Each domain has its own private API gateway and database for isolation and independence
- Platform is the only shared dependency across all domains
- Domains communicate via event-driven architecture using DynamoDB Streams for data replication
- Public/external API exposure should be synchronous via API gateways
- Goal: Each domain should be deployable independently to different AWS accounts
- Benefits: Team autonomy and flexibility to publish domains to multiple gateways

### Current Domains in Payments and Revenue

- Platform (shared foundation, not part of payments scope)
- Configs
- Products
- Billing Portals
- Proposed new domains: Patients/Customers and Subscriptions
- Additional domains mentioned: Invoices, Prescriptions
- Future consideration: Payment Providers as separate domain

### Future Identity and Authentication Changes

- Identity and auth service planned for managing external partner API tokens
- Once implemented, partners will use tokens instead of sending config ID in requests
- This will require API consumers to update their access patterns

### Concerns Raised About Architecture Complexity

- Connor raised concerns about significant overhead and plumbing being built for relatively small domain coverage
- Questioned whether the microservices approach at this granular level is worth the infrastructure investment
- Clint flagged concerns about collaboration requirements and velocity impact from DynamoDB Streams connections
- Brian noted the architecture appears convoluted with many API gateways for a single domain
- Team acknowledged that one API gateway with Swagger definitions might be simpler
- Connor emphasized importance of understanding trade-offs and offered Stripe's experience with users at similar scale

- Automatic retry capability to avoid returning errors to users
