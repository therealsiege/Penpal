### Multi-Tenancy Architecture Overview

- MedPlum segregates data at multiple levels: projects (dev/staging/production), users, and tenants within projects
- OpenLoop will likely use two-tier tenancy: organizations (representing clients) and healthcare services (representing verticals like medical weight loss, TRT)
- Patients will be assigned to one or more tenants; all related data automatically inherits the patient's tenant assignments through the patient compartment
- Tenants are defined using the `meta.account` field on FHIR resources

### Organization and Client Structure

- Clinicians currently see patient data based on organization assignment and which tickets they pick up
- Current architecture uses clinic app as middleware layer that manages Healthy API key mapping and authentication
- Team confirmed plans for middleware layer that handles authentication and routes requests to appropriate MedPlum organizations
- MedPlum supports multiple authentication patterns: native identity provider, external identity provider, or token exchange

### Access Control Capabilities

- Access policies can be more restrictive than tenant boundaries, controlling visibility down to specific resource types and fields
- State-based access control is possible (e.g., clinicians only seeing patients in states where they're licensed)
- Access policies support very granular controls including field-level visibility, write constraints, and status-based permissions
- Users can have access to multiple tenants through parameterized access policies

### Healthcare Service Tenants for Verticals

- Protocol and questionnaire templates for each vertical (medical weight loss, TRT, etc.) will be stored in healthcare service tenants
- Templates will be shared across organizations through access policy assignments rather than duplication
- Providers and partner API users will receive read-only access to relevant healthcare service resources

### Enterprise Master Patient Index (EMPI)

- Future initiative discussed for canonical patient records across multiple organizations
- EMPI pattern allows linking duplicate patient records from different tenants while maintaining data segregation
- Master patient index exists outside tenant boundaries to provide deduplicated view of entire patient population
- Common pattern for large healthcare organizations with multiple clinics

### Current Order Management Challenges

- The current system relies on a Google Sheet to manage pharmacy orders, which is not scalable as multiple pharmacies are added
- Compliance concerns exist around pharmacies seeing all patient data across all clients in a single sheet
- The system needs to segregate data so each pharmacy only sees patients whose orders are assigned to them (e.g., Triad should only see their assigned orders, not Cadre or Beaker's)
- Current tracking is patient-level rather than order-level, making refill management difficult
- Lakshmi is working on a related project but this order management system is separate

### Current Workflow Process

- Patients complete intake and identity verification, with information collected at intake level
- Patient information populates into a Google Sheet organized by client (Taurus, Enhanced Games, ULO, Titan, Rouge)
- Providers write prescriptions in DoseSpot (external system not controlled by the team) after reviewing lab results
- Prescriptions automatically go to pharmacy's fulfillment queue
- Pharmacy staff must manually check the Google Sheet to verify patient information and payment status before processing orders
- Sheet uses color coding: green indicates paid patients ready to ship, red indicates unpaid orders that create backlogs
- Triad pharmacy currently has approximately 2,000 unpaid orders in backlog
- Pharmacy must check multiple tabs (Open Loop, Q tab) depending on client to locate patient information
- Technical breaks between systems (Persona/Plaid to Healthy to Google Sheet) occasionally prevent patient information from populating correctly

### Payment Pathways

- Two different payment methods currently in use: pay before consult and pay after consult
- Rouge and Titan use the pay-after model, requiring the Q tab system to track when payments are received
- Taurus patients use pay-before model, making them easier to process as payment is already collected
- The team must coordinate with pharmacies on which orders to ship based on payment status, as pharmacies don't normally track payment in their own systems

### Data Privacy and Compliance Concerns

- Current Google Sheet shows all patients from all Open Loop Health clients to any pharmacy accessing it
- This creates compliance concerns about data exposure
- When orders are written to different pharmacies (Triad, Cadre Labs, Beaker), each pharmacy should only see data for orders assigned to them
- The pharmacy's role is to verify patient identity and driver's license information, not to manage payment

### Technical Requirements

- Need a system that can programmatically manage order routing rather than relying on manual Google Sheet updates
- System must integrate with DoseSpot (external prescribing system) to read API requests and track orders
- Solution may not require building new technology from scratch
- Mitch is working on finalizing workflow documentation to support the solution
- Pharmacy transfers are challenging and would require new prescriptions to be written; goal is to manage distribution through state matrix instead
