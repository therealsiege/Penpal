### Why MedPlum and FHIR

- Healthcare developers face a choice between non-developer-friendly EHRs or building compliance software from scratch
- MedPlum provides a middle path with developer-friendly tools and FHIR-native data storage
- FHIR enables interoperability with labs, prescribing, insurance, and HIE integrations
- Starting FHIR-native is preferable to maintaining translation layers on top of proprietary data models
- Translation layers require ongoing maintenance and can degrade over time

### MedPlum Architecture

- Firebase data store with access policies, subscriptions, and FHIR REST API
- JavaScript/TypeScript SDK available as a wrapper on top of REST API
- React component library (Storybook) for interacting with FHIR APIs
- MedPlum bots are serverless functions (AWS Lambdas) for internal automation
- All clinically-related data must be stored as FHIR resources
- GraphQL endpoint available as alternative to REST, but has rate limiting considerations

### FHIR Data Modeling Fundamentals

**Three Critical Pieces of FHIR Data Modeling:** 

- **Structure**: Which FHIR resources to use for representing data
- **Terminology**: How to tag and identify data with appropriate codes (e.g., LOINC codes for observations)
- **Lifecycle**: How resources change throughout the workflow

**Three Types of FHIR Resources:** 

- **Request resources**: "Please do this" actions (e.g., MedicationRequest for prescriptions, ServiceRequest for lab orders)
- **Event resources**: Recording what actually happened (e.g., Encounter, Observation, Procedure, Communication)
- **Definition resources**: Templates or protocols (e.g., Questionnaire for intake forms, PlanDefinition for clinical protocols)

**FHIR Resources Overview:**

- Approximately 150 different resource types available, but most builds use 10-20 resources
- Resources are JSON objects with standardized structure
- Resources link to each other using references (similar to foreign keys)
- Identifiers allow linking external IDs (e.g., SSN, medical record numbers) to FHIR resources

### Terminology Services and Value Sets

**Code Systems:**

- Standard healthcare code systems include LOINC, SNOMED, CPT, ICD-10, NDC, RxNorm
- Codable concepts can have multiple codings from different systems representing the same concept
- Code systems are already integrated into MedPlum projects (ICD-10, CPT, LOINC, etc.)

**Value Sets:**

- Group specific codes together for semantic purposes
- Used to define answer choices in questionnaires
- Can create custom value sets for OpenLoop-specific needs (e.g., medical weight loss disqualification comorbidities)
- Value sets are referenced in questionnaire items using URLs/URIs

### Search and Data Retrieval

**Two Options for Retrieving Data:**

- REST endpoint (recommended for most use cases)
- GraphQL endpoint (useful if team already familiar with GraphQL, but has rate limiting considerations)

**MedPlum TypeScript SDK:**

- Wrapper on top of REST API with built-in authentication
- Easiest way to get started
- Team already using SDK for some operations and finding it easy to use
- Open to pull requests for additional functionality

**Search Capabilities:**

- Search parameters and modifiers available
- Chain search supported

### Questionnaire Implementation

- OpenLoop currently uses Oaks funnel for patient intake, storing results in Hathi
- Goal is to post intake data to MedPlum instead of Hathi
- Oaks funnel already handles rendering and client-side validation

**Questionnaire Structure:**

- Questionnaires are JSON templates defining questions and possible answers
- Items can be groups or individual questions with nesting support
- Question types include string, date, choice (with value set references)

- Focus is on posting final results to MedPlum, not rebuilding validation

### Repository Overview

The payments and revenue repository serves as an entry point to Stripe services and endpoints, providing an abstraction layer so other services don't need direct knowledge of Stripe.  The repository contains more than just API integration—it includes significant business logic. 

**Three Main Domains:**

- **Configs**: Payment integration and configuration between clinic organizations and Stripe
- **Products**: Everything related to products, bundles, and prices
- **Billing Portals**: Self-service portals provided by Stripe where users can cancel subscriptions and receive retention incentives

The architecture is domain-driven, similar to the clinic repository structure. 

### Deployment Process

**Platform Dependency:**

The only dependency is the platform repository, which contains all shared infrastructure needed to deploy other projects. Platform must be deployed first before any other repositories.  All future repositories will also depend solely on platform. 

**Required Manual Setup:**

Several hosted zones must be created manually in AWS before deployment:

- Partners API
- Integrations API
- Internal API
- OUID org and path (values to be provided by Renato from platform team)

Other required values include Stripe ESL key and allow account IDs, though throttling, reserved concurrent execution, and geo-restriction are not mandatory. For local environments, developers just need to add their own account ID. 

**Deployment Workflow:**

1. Deploy platform repository
2. Copy CDK output values from terminal after platform deployment
3. Paste these values into the payments and revenue environment configuration
4. Deploy payments and revenue 

Scott created a mapping document showing which platform outputs map to which payment/revenue configuration values and shared it in the chat. 

### Code Structure

The repository follows a familiar folder structure similar to the clinic repository and core domains, with comprehensive documentation in the folder structure guidelines.  

**Main Folders:**

- **Features**: Contains the main functionality being created (e.g., REST API, events)
- **CQRS**: Commands (write operations) and queries (read operations) where main business logic lives
- **Domain**: Business entities, interfaces, enums, and cross-domain types
- **Data**: DynamoDB table schemas
- **Infrastructure**: Actual infrastructure creation for each domain
- **Utils**: Self-explanatory utilities

**Handler Guidelines:**

Handlers should remain thin—if logic exceeds 40 lines, it should be moved into a command or query in the CQRS folder.  The team uses DTOs (Data Transfer Objects) to standardize validation and create operable contracts. 

### Subdomains vs Domains

Subdomains are used for entities that cannot exist independently and require a parent domain for context.  The primary example is prices, which only make sense in the context of a product.  Subdomains use the same folder structure as regular domains, making it easier to promote them to full domains if needed in the future. 

In practice, creating a new domain is almost always preferable to creating a subdomain—subdomains are only appropriate for very specific cases. 

### Infrastructure and Constructs

The project uses the OpenLoop Health constructs package to define infrastructure for subdomains, domains, API gateways, event buses, and networking.   The team follows a rule of using existing constructs from the package instead of regular AWS CDK types and classes whenever possible.
