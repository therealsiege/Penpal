### FHIR Data Modeling: Three Layers

The session covered the three core layers of FHIR data modeling :

- **Definition resources**: Questionnaires, plan definitions, value sets, code systems - define the structure of data collection
- **Request resources**: Medication requests, service requests, appointments - represent orders or plans
- **Event resources**: Questionnaire responses, observations - record what actually happened

### Parsing Questionnaire Responses to FHIR Resources

The team reviewed how to transform questionnaire responses into appropriate FHIR resources  :

- **Patient demographic information** (name, DOB, address, gender) maps to the Patient resource
- **Height and weight** should be stored as separate Observation resources with appropriate coding (likely ICD-10 codes)
- **Weight loss goals** map to Goal resources, typically part of care plans
- **Medical conditions and comorbidities** (pregnancy status, liver disease, etc.) are stored as Observation resources

The team examined the Observation resource documentation, noting that status and code are required fields . Observations can reference the practitioner, patient, or care team member who made the measurement .

### Determining Appropriate FHIR Resource Types

Luis asked how to know which FHIR resource type to use for different data elements . Clint provided guidance:

- Most medically-related information is an Observation resource
- Most customers use only 10-20 FHIR resource types regularly: medication requests (prescriptions), service requests (lab orders), appointments, etc.
- Special cases include AllergyIntolerance resources for allergies and specific resources for social determinants of health
- Team has direct access via Slack for questions about nuanced cases
- Cursor AI can help identify appropriate resource types

### SOAP Notes and Provider Review Workflow

Luis asked how to track which clinician reviewed questionnaire information  . Clint explained the SOAP note workflow   :

- Parsed resources are surfaced to providers in a SOAP note format (Subjective, Objective, Assessment, Plan)
- Observations appear in the Objective section
- A Provenance resource records when a physician "signs off" that they've reviewed all information
- This bundles the resources together as a reviewed package

### Questionnaire Response Storage Strategy

Luis asked whether to store questionnaire responses first and then parse, or create resources directly via SDK  . Clint explained the reasoning  :

- **For intake questionnaires**: Always store the questionnaire response first, then parse via bot
    - Provides developer comfort - if parsing logic is incorrect or needs changes, questionnaire responses can be re-processed
    - Makes it easy to re-trigger workflows without losing data
- **For on-rails workflows** (like scheduling): Can create resources directly without questionnaire response intermediate step

### Plan Definitions and Care Templates

The team reviewed plan definitions as definition resources that can provision multiple resources at once  :

- Example shown: "Simple initial visit" plan definition that provisions questionnaire responses for vital signs assessment and activity definitions for labs
- Can be applied to patients through the Medplum provider interface as "care templates"
- When instantiated, creates a bundle of tasks that can be assigned to different providers (nurses, physicians, etc.)
- Tasks can be organized into hierarchies with dependencies as needed

Luis noted plan definitions seem similar to "programs" in their current system, which define questionnaires, lab requests, and medication requests for specific care pathways . Christina expressed excitement about this alignment with their care coaching workflows  .

### Source Control and Deployment

Discussion about managing templating resources (questionnaires, plan definitions) across environments  :

- Recommendation: Develop in dev project, store in GitHub source control, then propagate to staging and production
- Some customers use GitHub release CI/CD pipelines to deploy directly to Medplum
- Others write separate scripts and run manually on a schedule (weekly, monthly)
- Medplum aims to be agnostic about dev tools - will support whatever approach teams prefer

Luis mentioned existing tools like Click2Deploy where documentation can be modified, creating multiple places where changes can occur  .
