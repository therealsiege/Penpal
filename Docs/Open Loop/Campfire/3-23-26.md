### Architecture Overview

Renato presented the approved architecture for the payment domain consolidation   :

- All payment-related functionality will be consolidated into one payments domain, with the configs table being reusable across all other domains to reduce duplication
- The architecture will leverage subdomains within the payments domain:
    - Customer domain with two subdomains: subscriptions and invoices
    - Products and prices subdomain
    - Billing portals will become a full domain with its own table and CRUD operations
    - Coupons subdomain
- Each domain will have its own table, with strategic subdomains designed for easier data access

### ESL Ticket Dependencies

The team discussed several ESL tickets and their relationships :

- ESL 67 and ESL 49: Both requesting similar functionality, with 49 being the payment check orchestrator that will use much of 67 to replace the payment check function
- Clinic app is using ESL 50, 51, 53, and 54
- ESL 53 and 54 are invoices and subscriptions respectively, shaped at a much lower level of detail
- These may become what ESL 67 uses and points to when ready

### Event-Driven Architecture Approach

The architecture will use an event bus for communication with payment providers like Stripe  :

- Transactions will be saved to internal databases first, then events will be submitted to reflect changes to the payment provider
- The system won't wait for synchronization with the payment provider - data creation is instant, and synchronization happens eventually
- This approach decouples the payment provider from the domain logic, so provider failures don't cause system failures
- The event bus includes built-in retry logic
- Internal databases will be the source of truth, not Stripe

### Communication Patterns

- All communication to payment providers will be via event buses
- Communication between domains will remain synchronous via API Gateway
- Stripe currently emits events to the event bus, enabling two-way communication, though this isn't needed yet
- All Stripe dashboards will be read-only - changes must be made through Click to Deploy

### Technical Concerns Raised

Connor raised significant concerns about the event-driven architecture approach     :

- CRUD operations are inherently synchronous, and introducing asynchronous events in the middle of operations like "get product" or "create product" will make troubleshooting extremely difficult
- Tracing a single request through multiple event buses and systems will be a "nightmare to maintain"
- Event-driven patterns work well for fire-and-forget scenarios (like Stripe webhooks), but emitting events in the middle of operations when data is in an unstable state introduces unnecessary complexity
- The decoupling should happen at the ESL layer, not the event layer - that's the purpose of the ESL

### Architectural Direction Rationale

Renato explained the rationale for the event-driven approach    :

- Event-driven architecture (EDA) is a non-negotiable direction for OpenLoop as a whole
- This applies to all providers and even inter-service communication
- The approach is inspired by companies like Uber and LinkedIn that are fully event-driven
- The internal databases must be the source of truth, not the payment provider
- As long as data exists internally, it's "good enough" to start working - synchronization with providers can happen later
- The team is not currently worried about consistency between platforms

### Data Ownership Requirements

For the architecture to work  :

- OpenLoop must own all data and store it in internal databases
- All GET operations will hit internal databases
- All transactions will hit internal databases and emit events to reflect data to providers
- Features like billing portals that currently have no table and make direct calls to Stripe will need to be redesigned to store data locally first

### Payment Processing Clarification

- The architecture shown creates information but doesn't handle the actual payment process
- Renato acknowledged that actual payment processing likely needs to be synchronous but hasn't discussed this with Alex yet
- The question of whether OpenLoop should continue operations (like scheduling appointments) if a customer's payment fails during signup remains unresolved

### Architecture Overview

- New domain structure centers around a payments domain containing customers, subscriptions, invoices, products, and other subdomains
- Customers subdomain will contain subscriptions and invoices for easier data access
- All domains will share a configurations table for communicating with payment providers like Stripe
- Coupons may be moved inside products subdomain if tightly coupled
- Current structure in configs and products is already in dev and production

### Data Storage Strategy Decision

- Team decided NOT to backfill all customer data upfront, unlike the approach taken with products
- Will use a cache approach instead: store customer data in local table only as it's accessed
- Customer table will store minimal data: just IDs (Stripe ID, healthy org ID, open loop org ID) and email addresses
- Next lookup for same customer will use cached data instead of calling Stripe again
- This avoids the 2-6 month delay that would be required for full data backfilling

### Synchronous vs Event-Driven Architecture

- Long-term goal is fully event-driven architecture where all inter-domain communication uses asynchronous events
- However, team acknowledged that immediate term requires synchronous API calls to Stripe
- Event-driven approach won't work currently because multiple systems (MedVis, OAPS, etc.) still communicate directly with Stripe
- Once all consumers switch to calling payments domain instead of Stripe directly, can move to event-driven model
- Short-term compromise: use same folder structure and scaffolding as target architecture, but with synchronous calls

### Concerns About System of Record

- Major pivot revealed: ESL is no longer just an integration/abstraction layer but is becoming the system of record for payment data
- This represents a significant change that wasn't clearly communicated to the team
- Products domain already made this transition - UPI no longer stores products and instead calls payments domain
- Team expressed concerns about optimizing differently for system of record vs integration layer
- Potential future change: customers entity may need to move outside of payments domain

### Data Synchronization Challenges

- Products were backfilled in 3 days using a script, with parallel work on queries and schema continuing
- Customers/subscriptions/invoices present more challenges because they change frequently in real-time
- Customers update payment methods, manage subscriptions via billing portals, receive payment reminder emails - all causing constant changes
- Webhooks considered for keeping data in sync, but determined they don't provide enough benefit over cache approach for this use case
- Team acknowledged that synchronous calls to Stripe remain necessary to get source of truth

### Implementation Approach

- All API calls will go through ESL (API Gateway), maintaining proper architecture boundaries
- Example flow: Clinic App requests customer subscriptions/invoices → calls ESL → ESL makes synchronous Stripe API calls → returns results
- Renato and Scott to coordinate on code organization, with Scott's existing code fitting into new domain structure
- Scott will create abstraction layer for customer access that can point to table now, API Gateway later
- Configs table must be moved into payments domain as prerequisite, work starting immediately

### Team Dynamics and Process Concerns

- Renato acknowledged taking "arrows from both sides" as the messenger between different parts of the team
- Frustration expressed about feeling out of the loop on major architectural decisions
- Need identified for better inclusion of team members in decision-making process
- Goal is to find compromise between ideal future architecture and what's achievable with current constraints
- Team emphasized importance of understanding whether building integration layer or system of record

### Technical Considerations

- Event Bus discussed as centralization point for reporting and alerts, despite concerns about single point of failure
- AWS Event Bus appears to have sufficient throughput for anticipated load, though team acknowledged need to verify
- Domain-driven design aims for isolation where each domain is independent project not depending on others
- Asynchronous events enable loose coupling so failure in one domain doesn't affect others
- Team acknowledged this adds complexity but recognized benefits for scale and resilience
