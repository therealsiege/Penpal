### Architecture Consolidation Decision

The team agreed to consolidate the current multi-domain architecture into a single monolithic "payments and revenue" domain with nested subdomains.   Currently, the system has three separate independent stacks (configs, products, billing portals) which are causing significant complexity and latency issues.  

Curtis from Stripe recommended building this as one monolithic service with modular structure, similar to how other large-scale customers approach this problem.  This approach allows for easier future separation when teams grow or different scaling needs emerge, but avoids premature optimization.  The new structure will have configs at the parent stack level, with all other components as nested stacks that can directly reference the config data.  

### Current Architecture Problems

The team identified several critical issues with the current multi-stack approach:

**Latency and Data Replication Issues:** DynamoDB streams are being used to replicate config data across three separate domains, causing delays between when a configuration is created and when it becomes available in dependent domains.  This latency will worsen as traffic increases since streams operate through a buffer.   The team is also paying three times the storage cost for the same config information replicated across domains. 

**Development and Deployment Complexity:** Developers are struggling to set up development environments and understand how to deploy and connect across domains.   Cross-stack dependencies require careful deployment ordering and complex exports, making DevOps significantly more difficult.  The bulkheads between stacks are adding cognitive overhead and operational complexity.  

**Infrastructure Overhead:** Each independent stack requires its own infrastructure setup, including API gateways and DynamoDB streams, adding unnecessary cost and complexity for the current scale.  

**Documentation Gap:** Poor internal documentation around the new tooling and platform is contributing to setup difficulties, though this is being addressed separately.  

### Patient/Customer Domain Discussion

The team debated whether to include a customer domain within the payments ESL or rely on a separate patient domain.   Curtis raised the important consideration that a single patient may map to multiple customers across different payment processors (Stripe, ChargeBee, etc.).  

**Multi-Processor Complexity:** The team identified scenarios where one patient might need multiple payment processor accounts - for example, TRT (controlled substance) transactions cannot use Stripe due to underwriter restrictions, requiring a different processor even when cross-selling to existing customers.   This means the patient identity system needs to map one patient to potentially multiple customers across different payment platforms.

**Brand Boundaries and Patient Trust:** Curtis highlighted the importance of not bleeding patient information across brand boundaries, as patients may not know that OpenLoop services multiple brands they interact with.   The patient identity work being done by Jamie and Jose defines three tiers: source records per vendor, patient records per organization/brand, and a canonical human identifier at the top level for fraud detection.  

**Short-Term Solution:** Since the full patient identity system is not ready, the team decided to create a temporary patient/customer mapping subdomain within payments and revenue.   This will eventually be migrated to the broader patient identity domain once available. 

### Event-Driven Integration Approach

The team discussed shifting from synchronous Stripe API calls to an event-driven architecture.  This approach will loosely couple the system from Stripe as a dependency and improve retry handling. 

**Event Flow Design:** When a product is created, it will first be saved to the database, then publish an event to the payments event bus.  A separate event handler will consume this event and make the asynchronous call to Stripe, then update the database with the Stripe-generated ID.   The team will use EventBridge pipes to prevent infinite loops by filtering out updates that only change the Stripe ID.  

**Stripe Webhook Integration:** Stripe is already an EventBridge partner, so the system can directly listen to Stripe events without setting up separate webhook endpoints.   For products, since Stripe will be configured as read-only, the team doesn't need to listen to product creation/update events from Stripe.  However, for customer address updates and similar scenarios, the system will need to consume Stripe events to stay synchronized.  

**Idempotency and Error Handling:** If a Stripe call succeeds but the database update fails, the retry from the dead letter queue will include the Stripe ID to prevent duplicate creation.   The team will implement appropriate error handling logic at the Lambda level rather than relying solely on additional events.

### Technical Implementation Details

**Stack Structure:** The change involves moving from multiple independent stacks to a single domain stack with nested stacks for each subdomain.   Each subdomain can still create its own route paths through the API proxy.   This eliminates the need for DynamoDB streams and cross-stack references while maintaining logical separation. 

**Domain Organization:** The team plans to have a broad "payments and revenue" domain with subdomains for configs, products, billing portals, customers, subscriptions, and eventually disputes, invoices, refunds, and other payment lifecycle components.  The general principle is to start with broadly scoped domains and break them up later if needed, rather than starting too granular.  

**Config Accessibility:** With configs at the parent stack level, all nested subdomains will have direct database access without needing replication.  The minor delay in config availability (seconds) is not a concern since configs are set up infrequently and not consumed in real-time.  

**Subdomain Independence:** While consolidating into one stack, the team will maintain disciplined modularization through subdomains to avoid creating a "big pile of mud."  Subdomains should still be cautious about reaching across into other tables where possible. 

**Future Flexibility:** The modular approach will make it relatively straightforward to move a subdomain to its own independent domain later if needed, though the team wants to avoid analysis paralysis and focus on getting things working first.
